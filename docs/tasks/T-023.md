# T-023 createPostIntegration 트랜잭션화 (I-08)

상태: done
계획: docs/IMPROVEMENT_PLAN.md §T-023

## 목표 (한 문장)
`PostIntegrationRepository.createPostIntegration`의 SELECT→UPDATE→UPDATE→INSERT 연쇄를 `dbManager.transaction` 안에서 실행해, 중간 실패 시 부분 반영(예: 기존 연동은 비활성화됐는데 새 INSERT는 실패)을 막는다.

## 측정 (2026-09-22, Claude)
- `src/repositories/forum/PostIntegrationRepository.js:14-105` `createPostIntegration`: `this.dbManager.query` 6회(SELECT 3, UPDATE 2, INSERT…ON CONFLICT 1), 트랜잭션 없음. **이 태스크의 유일한 대상.**
- 같은 파일의 `ensureForumMapping`, `createDefaultForumRecord`, `linkVoiceChannel`, `setStandaloneMode`, `deactivatePostIntegration`: 각각 단일 문장(upsert/UPDATE)이라 원자적 → 대상 아님. `getOrCreateForumRecord`(SELECT→INSERT ON CONFLICT)도 upsert가 멱등이라 제외.
- `DatabaseManager.transaction(callback)` (`src/services/DatabaseManager.js`): `pool.connect()` → `BEGIN` → `callback(client)` → `COMMIT`/`ROLLBACK` → `release()`. 콜백 안에서는 **`client.query`** 를 써야 같은 커넥션에 묶인다.

## 변경 (이 메서드 한 곳만)
1. 메서드 본문 전체를 `return await this.dbManager.transaction(async (client) => { ...기존 본문... });` 로 감싼다.
2. 본문 안의 `this.dbManager.query(` 6회를 전부 `client.query(` 로 바꾼다 (SQL·params·분기·로그·throw는 **그대로**).
3. 기존 `try { ... } catch (error) { logger.error(...); throw error; }` 구조는 유지 — transaction 바깥에 두면 ROLLBACK 후 재throw된 에러를 그대로 로깅하므로 의미 동일. 어느 쪽에 두었는지 보고.
4. 다른 메서드·파일 수정 금지.

## 테스트 (`tests/repositories/ForumRepository.test.js` 의 `createPostIntegration` describe 갱신 + 추가)
- 기존 3케이스는 `fakeDbManager.query` mock을 쓰므로 실패하게 된다. `fakeDbManager.transaction = vi.fn(async (cb) => cb(client))` 와 `client = { query: vi.fn() }` 로 바꿔 **같은 시나리오**를 유지한다 (기대 SQL·params·반환값 동일).
- 추가 2케이스: (a) 정상 경로에서 `transaction`이 정확히 1회 호출되고 `dbManager.query`는 0회; (b) 콜백 안 두 번째 쿼리가 reject하면 에러가 그대로 전파되고(`rejects.toThrow`) 이후 쿼리는 호출되지 않음 (ROLLBACK 자체는 DatabaseManager 테스트가 담당).
